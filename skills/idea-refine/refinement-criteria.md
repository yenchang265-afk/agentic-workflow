# Refinement and Evaluation Criteria

The Phase 2 rubric. Weigh only the dimensions that bear on this idea; a
direction scored on all of them evenly has not been judged.

## User value — the dimension the rest depend on

**Painkiller or vitamin**, decided by evidence rather than by how the idea
sounds. A painkiller shows up as emotion in how people describe the problem,
workarounds they already built, and a frequency high enough to keep it present.
A vitamin gets a polite nod and no behaviour change.

The questions that produce that evidence: name three specific people with the
problem now; what are they doing today *instead* — the current workaround is
always the real competitor; what would make them switch; how often do they hit
it; and is this pull (they are asking) or push (you think they should want it).

Three answers that mean the value is not there yet: "everyone could use this",
"it's like X but better", and a real problem that is genuinely rare — intensity
without frequency rarely carries a product.

## Feasibility

Split the technical question from the practical one. Technically: does the core
capability exist and work reliably, what is the hardest part, and how much of it
depends on third parties you do not control. Practically: the minimum effort to
an MVP, expertise you would have to acquire, and any regulatory or compliance
gate. Then time-to-value — is there a version in front of users in weeks rather
than months?

"We just need to solve [hard research problem] first", several dependencies that
must all land together, and an MVP still months out are each a signal the shape
is wrong, not that the schedule is.

## Differentiation

Different, not better — and durable enough that a competitor cannot copy it in a
week. The ladder, strongest first:

1. A capability that did not exist
2. A 10× improvement large enough to change behaviour
3. An existing capability brought to an audience that was excluded
4. A context where the existing solutions fail
5. The same capability, dramatically simpler
6. The same thing, cheaper — the weakest, and the first to be competed away

Differentiation that lives entirely in the technology, or in a feature users
rank below the ones they already have, is not differentiation.

## Assumption audit

Every direction sorts its assumptions into three tiers, because the tier decides
what happens next:

- **Dealbreakers** — wrong, and the idea is dead. Validate these *before*
  building anything.
- **Important** — wrong, and the approach changes but the core survives.
- **Nice to have** — secondary features and optimisations. Do not spend
  validation on these until the core is proven.

## Choosing

High value and high feasibility goes first; high value and low feasibility is
the one worth the risk; low value and high feasibility only if it is trivial;
low value and low feasibility is a no. Differentiation breaks ties inside a
quadrant.

## MVP scoping

One job done well, not three done partially. The MVP's purpose is to test the
riskiest assumption, so it is scoped by time-box rather than by feature list.
The "Not Doing" list is mandatory — it is what stops the scope creeping back in.
And if the first version is not slightly embarrassing, it shipped later than it
should have.
