# 50 —— 怪罪建置之前，先確認紅色檢查

**狀態：已實作。**

## 問題

`runChecks` 對每個發現的檢查只跑一次，非零退出碼就成為 checks 軸上的 `critical`
發現，把階段壓成 FAIL。一個不穩定（flaky）的測試套件因此把迴圈送回 BUILD，帶著
一個不存在的缺陷——而被要求修它的 BUILD，改了本來沒問題的程式碼。燒掉一次迭代，
外加一份沒人要的 diff，只因為一個迴圈本可再跑一次就驗證的訊號。

## 改了什麼

- **只重跑一次，且只對 `fail`**（`CHECK_RERUNS = 1`）。`error` 從不重跑（缺少的
  runner 不會回來），`pass` 也不會。`onCheck` 每**次執行**觸發一次，所以重跑會在
  自己的 cap 下重新蓋章 claim。
- **先敗後過就是 FLAKY。** 結果的 `outcome` 是重跑的 `pass`——階段不被壓低——但
  帶著 `flaky: true`、`reruns: 1`，以及**第一次**失敗執行的尾巴作為 `output`：那
  才是人類想看的證據；通過的那次沒印出值得讀的東西。兩次都失敗則保留第二次的
  退出碼與輸出，並帶 `reruns: 1`。
- **flake 會到達每個該看到的人。** `checksBlock` 把該行標成 `FLAKY … name it in
  your verdict` 並渲染第一次執行的輸出；`checkAxis` 為它加一個 `suggestion`
  發現——非阻擋，所以壓底不會觸發，但由 `suggestionFindings` 帶到 ship 把關點，
  「這個套件不穩定」是該權衡的事實。`persist.ts` 宣告這兩個欄位，恢復的執行不會把
  flake 渲染成普通 PASS。
- **`checksBudgetMs` 把重跑算進去。** 預算是該階段的上界，stage-marker 的期限由它
  公告；只算單次執行的總和會讓重跑階段活過自己的期限，被讀成已死的執行。

## 尖銳邊角

- **永遠不重跑 `error`。** 127 是「二進位不在這裡」，124 是卡住；再跑一次只是付
  整個 cap 換同樣的答案。
- **真正紅的套件也要付這次重跑**——一次。這是不把測試框架的問題怪到建置頭上的
  代價，而一次執行是區分 flake 與失敗的下限；沒有旋鈕，因為付不起一次重跑的套件
  也當不起把關。
- **flake 不是「沒話說的 PASS」。** 丟掉第一次執行的輸出或那個 suggestion，會讓
  迴圈自己的把關悄悄變得不確定，而那正是檢查階段存在要消除的缺陷。
