# Azure DevOps MCP tool surface (contract)

Generated by dumping `tools/list` from `npx -y @azure-devops/mcp@2.8.1 <org> -d repositories -d pipelines`.
`listTools()` runs before any Azure authentication, so this needs no PAT.

**This file is the contract.** Every tool name and argument spelling in `packages/core/src/source/ado-tools.ts`,
in the `{{#platform.ado}}` stage-prompt blocks, and in the generated agent `tools:` frontmatter is taken from here.
Regenerate it when the pinned server version changes, and re-check every name that moved.

- Server version: **2.8.1** (pinned; do not use `@latest`)
- Domains enabled: `repositories`, `pipelines` → **36 tools**
- Auth choices: `interactive` (default), `azcli`, `env`, `envvar`, `pat`

> **Version warning.** `docs/TOOLSET.md` on the upstream `main` branch documents a *consolidated*
> surface (`repo_pull_request` + an `action` argument) that is **not released**. Shipped 2.8.1 uses the
> flat one-tool-per-verb names below. Do not plan against the upstream doc.

## Notes that bit during design

- `repo_list_pull_requests_by_commits` takes `repository`, **not** `repositoryId` — the only tool that spells it that way.
- `fullResponse` exists on `repo_list_pull_request_threads` and `repo_list_pull_request_thread_comments`, but **not** on
  `repo_list_pull_requests_by_repo_or_project`. Whether that list trims `reviewers`/`createdBy`/`forkSource` is
  UNVERIFIED and must be confirmed against a live org before the poller trusts it.
- `pipelines_get_build_log_by_id` takes `startLine`/`endLine` — use it to bound log excerpts instead of pulling whole logs.
- `pipelines_get_builds` supports `branchName`, `resultFilter`, `statusFilter`, `queryOrder`, `top` — filter server-side.
- `PERSONAL_ACCESS_TOKEN` is base64 of `<anything>:<pat>`: the server decodes, splits on `:` and keeps everything
  **after the first colon** (`dist/index.js:63`). `base64(":" + pat)` is therefore correct and needs no identity.
  A base64 value with no colon in it decodes to an empty token and fails opaquely.
- There is no policy-evaluation tool. PR check state comes from `pipelines_get_builds`.
